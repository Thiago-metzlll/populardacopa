00 — Contexto

O que é o Popular da Copa

É um aplicativo mobile (feito com React Native — código que vira app de verdade no Android/iOS — usando o framework Expo) sobre a Copa do Mundo. Ele mistura três ideias num só produto:

  • Álbum de figurinhas — o usuário compra pacotes, abre e coleciona figurinhas de jogadores e seleções, como um álbum físico de Copa.
  • Apostas de palpite — o usuário arrisca um placar para partidas futuras e ganha recompensas (moedas ou figurinhas) se acertar.
  • Times e seleções — catálogo de seleções, elencos e estatísticas de jogadores.

Tudo isso gira em torno de uma moeda virtual: o usuário ganha moedas (apostas, recompensa diária) e gasta moedas (comprar pacotes/figurinhas). Esse saldo, junto com o progresso do álbum, é o dado "vivo" do app — e é justamente esse tipo de dado que faz sentido guardar num banco não-relacional na nuvem, como veremos na seção 08.

01 — Arquitetura

Clean Architecture, explicada sem jargão

Clean Architecture é só uma forma de organizar o código em camadas, de modo que a parte mais importante do sistema — as regras de negócio — não dependa de detalhes técnicos como "qual banco de dados eu uso" ou "como a tela é desenhada". Pense em cascas de cebola: no centro fica a regra do jogo; nas camadas de fora ficam os detalhes que podem mudar sem afetar o centro.

Conceito fundamental

Regra de dependência: uma camada só pode "conhecer" as camadas mais internas, nunca o contrário. A tela (Presentation) pode chamar a regra de negócio (Domain), mas a regra de negócio nunca sabe que existe uma tela, um botão ou um banco de dados específico.

Na prática, isso traz um benefício concreto para este projeto: dá para trocar "onde os dados são guardados" (de um repositório fake em memória para o Firestore de verdade) sem tocar em uma linha sequer das telas ou das regras de negócio. Foi exatamente isso que aconteceu com a feature de álbum — ela nasceu com um MockAlbumRepository e migrou para um FirestoreAlbumRepository real depois.

02 — Estrutura

As 4 camadas do projeto

O projeto segue exatamente este fluxo (a mesma seta que aparece na documentação técnica do repositório):

Presentation

a vitrine

Telas, componentes visuais e hooks (funções que guardam estado de tela, tipo "carregando / deu erro / aqui estão os dados"). É a única camada que sabe desenhar algo na tela.

↓ chama

Main (Composition Root)

o maestro

Funções chamadas factories (fábricas) que montam a peça final: pegam uma implementação concreta (Infra) e entregam pronta para a regra de negócio (Domain) usar. É o único lugar do projeto que conhece Domain e Infra ao mesmo tempo.

↓ injeta e chama

Domain

o núcleo — a regra do jogo

Os tipos de dado (ex: o que é uma "Figurinha", uma "Partida") e os use cases — casos de uso: uma classe por regra de negócio, com um único método execute(). Zero dependência de banco de dados, de React ou de qualquer biblioteca externa.

↑ implementa os contratos do Domain

Infra

o fornecedor

Onde a regra "como buscar dados" é implementada de verdade — hoje, principalmente o FirestoreAlbumRepository conversando com o Firestore. O Domain define o que precisa existir (uma interface); a Infra decide como fazer.

Boa prática do projeto

A Presentation nunca importa a Infra diretamente — sempre passa pela Main. Isso significa que um componente de tela nunca faz import { FirestoreAlbumRepository } diretamente; ele chama uma factory como makeGetUserProfile(), que devolve o use case já pronto para uso. A seção 03 destrincha essa regra linha a linha.

Exemplo real: uma factory

main/factories/makeGetUpcomingMatches.ts
// Função pura: monta o use case injetando o repositório concreto
export const makeGetUpcomingMatches = () =>
  new GetUpcomingMatches(matchRepositoryInstance);
03 — A regra na prática

A regra dos imports: por que uma camada não importa a outra

A seção anterior falou em "camadas que não conhecem umas às outras". Mas o que é, concretamente, uma camada "conhecer" outra? Em TypeScript a resposta é direta e um pouco brutal: conhecer é importar. Se um arquivo escreve import { X } from '...', ele passa a depender de X — não tem meio-termo, não tem dependência "leve". O arquivo não compila mais sem ele, não pode ser testado sem ele e não pode ser reaproveitado sem ele.

Por isso, neste projeto, a regra de dependência não é uma boa intenção escrita na documentação: ela é uma regra sobre quais linhas de import podem existir no topo de cada arquivo. É verificável, é fácil de auditar e é fácil de violar por descuido — daí a insistência.

A regra em uma frase

Os imports só podem apontar para dentro. Presentation importa Main e Domain; Main importa Domain e Infra; Infra importa Domain. O Domain não importa ninguém — nem React, nem Firebase, nem SQLite, nem outra camada.

O paradoxo: o Domain precisa de dados, mas não pode importar quem busca dados

Aqui está o nó que costuma travar quem está aprendendo. O caso de uso CreatePrediction precisa gravar um palpite no banco. Mas quem sabe gravar no banco é a Infra — e o Domain não pode importar a Infra. Como ele grava, então?

A saída é inversão de dependência: em vez de o Domain procurar alguém que saiba gravar, ele declara o que precisa e deixa outro alguém cumprir. Essa declaração é uma interface — um contrato sem implementação — e ela mora dentro do próprio Domain.

domain/repositories/MatchRepository.ts o contrato
// Só descreve O QUE precisa existir. Nenhum import de banco aqui.
export interface MatchRepository {
  getUpcomingMatches(): Promise<Match[]>;
  getMatchById(matchId: string): Promise<Match | null>;
}
infra/repositories/SQLiteMatchRepository.ts quem cumpre o contrato
// Repare na direção: é a INFRA que importa o DOMAIN, nunca o contrário.
import { MatchRepository } from '../../domain/repositories/MatchRepository';

export class SQLiteMatchRepository implements MatchRepository {
  async getUpcomingMatches() { /* SELECT * FROM matches ... */ }
}

É isso que a seta apontando para cima no diagrama da seção 02 significa. A Infra se submete ao Domain, e não o Domain à Infra. O nome disso — "inverter" — vem justamente daí: numa arquitetura tradicional, a regra de negócio importaria a classe do banco; aqui a relação está de cabeça para baixo de propósito.

Em execução as setas são outras

O detalhe que confunde: em tempo de execução, o use case realmente chama o SQLiteMatchRepository. A independência não é uma ilusão nem um truque — ela existe apenas no código-fonte. As duas direções coexistem:

Nenhuma seta chega ao Domain vinda de fora.

Quem faz as duas colunas conversarem é a Main. Ela é o único lugar que escreve o nome concreto SQLiteMatchRepository e o entrega ao use case pelo construtor. O use case recebe "algo que cumpre o contrato" e nunca fica sabendo o nome de quem chegou.

main/factories/repositoryInstance.ts o único ponto de acoplamento
import { SQLiteMatchRepository } from '../../infra/repositories/SQLiteMatchRepository';
import { MockPredictionRepository } from '../../infra/repositories/MockPredictionRepository';

export const matchRepositoryInstance = new SQLiteMatchRepository();
export const predictionRepositoryInstance = new MockPredictionRepository();

Esse arquivo de cinco linhas é o motivo de a migração de mock para banco real ter sido barata: trocar MockPredictionRepository por uma implementação de verdade é editar uma palavra, em um arquivo. Nenhum use case, nenhum hook e nenhuma tela precisam ser abertos — porque nenhum deles jamais escreveu esse nome.

A mesma regra vale entre features

Quando um palpite é vencedor, o usuário ganha moedas — e moedas pertencem à feature album, não a apostas. A tentação seria importar o álbum dentro do use case de apostas. O projeto resolve isso do mesmo jeito: o Domain de apostas declara um contrato (RewardGranter) e só a Main de apostas conhece as factories do álbum.

main/factories/makeSettlePendingPredictions.ts
// apostas/domain não conhece album. Só este arquivo conhece os dois.
import { makeAddUserCoins } from '../../../album/main/factories/makeAddUserCoins';

export const makeSettlePendingPredictions = () =>
  new SettlePendingPredictions(predictionRepositoryInstance, matchRepositoryInstance, {
    grantCoins: async (userId, amount) => {
      await makeAddUserCoins().execute(userId, amount);
    },
    // ...
  });

Como auditar isso em 5 segundos

Como a regra é sobre texto no topo dos arquivos, ela se verifica com uma busca simples. Rodando no repositório hoje:

  • Domain importando Infra, Main ou Presentation: 0 ocorrências. O núcleo está limpo.
  • Infra importando Domain: 20 arquivos — e isso é o esperado, é a seta correta.
  • Presentation importando Infra: 2 ocorrências (ver abaixo).
Honestidade sobre o código real

As duas exceções são useAbrirPacote e useBuyStickerPack, que importam pendingPackStore — um cache em memória guardado em infra/stores/ para evitar sortear as figurinhas duas vezes. É uma violação real da regra, ainda que pequena: o correto seria expor esse cache por uma factory ou movê-lo para shared. Vale registrar como está, em vez de fingir que a arquitetura é 100% pura — reconhecer o débito é parte de estudá-la.

A regra que a direção dos imports não pega

Vale um alerta, porque é a confusão mais comum: ter os imports na direção certa não garante que o código esteja na camada certa. São duas perguntas diferentes, e só a primeira é verificável com uma busca de texto.

A feature de álbum ilustrou isso. O FirestoreAlbumRepository sempre respeitou a direção — ele importa o Domain, nunca o contrário. Mesmo assim, dentro dele moravam decisões que são regra de negócio pura: "recusar a compra se o saldo não cobre o custo", "um pacote tem 3 figurinhas", "o progresso se recalcula assim". Enquanto isso, o use case BuyStickerPack — a classe que leva o nome da operação — tinha uma linha só, repassando tudo ao repositório.

Conceito fundamental

Existem duas coisas diferentes chamadas de "orquestração": decidir o que acontece (checar saldo, sortear, calcular o novo progresso) é regra de aplicação e pertence ao use case; montar como aquilo é gravado (o objeto de update, o arrayUnion, o formato do documento) é detalhe do banco e pertence ao repositório. Misturar as duas dentro do repositório é o desvio mais comum — e o mais silencioso, porque nenhum import denuncia.

Hoje as duas operações de compra foram corrigidas: as regras voltaram para BuyStickerPack e BuyIndividualSticker, e o repositório ficou com um único método de persistência, commitStickerPurchase(), que grava o que já foi decidido — sem conferir saldo, sem sortear, sem calcular nada. Mas a correção alcançou 2 das 8 operações do repositório: o sorteio do pacote grátis, a recusa por cooldown da recompensa diária, o saldo inicial de 200 moedas e a regra "o saldo nunca fica negativo" seguem dentro da Infra. Não por acaso, os use cases dessas operações continuam sendo delegação de uma linha — mesmo sintoma, ainda não tratado. O inventário completo da pendência está em docs/testing-plan.md.

O ganho não foi só teórico. Com a regra no use case, o sorteio e o relógio passaram a ser injetáveis pelo construtor — e a compra virou testável de ponta a ponta sem Firestore nenhum. Antes era impossível afirmar "o saldo debitado é exatamente 150" sem simular um banco inteiro.

O teste que revela a camada errada

Um sintoma prático: se para testar uma regra de negócio você precisa simular um banco de dados, provavelmente a regra está na camada errada. Regra de negócio bem posicionada se testa com objetos simples em memória.

04 — Estilo de código

Por que tanta classe num projeto React?

Quem vem de React moderno estranha: hoje quase tudo em React é função — componentes são funções, hooks são funções, e classes praticamente sumiram do ecossistema. Só que ao abrir src/features/*/domain/ e infra/ aparecem 38 arquivos com export class. Não é apego a Java: cada lugar do projeto usa a forma que resolve melhor o problema daquela camada.

1. A classe existe para receber dependências pelo construtor

Este é o motivo principal. Um use case tem duas coisas de naturezas diferentes: com o que ele trabalha (o repositório) e o que ele faz (a regra). A classe separa fisicamente as duas: o construtor recebe as dependências e guarda; o execute() usa. É a injeção de dependência da seção anterior, materializada em sintaxe.

domain/usecases/CreatePrediction.ts
export class CreatePrediction {
  // "private readonly" no parâmetro já cria e trava o campo — atalho do TS
  constructor(private readonly predictionRepository: PredictionRepository) {}

  async execute(data: Omit<Prediction, 'id' | 'createdAt' | 'status'>) {
    return this.predictionRepository.createPrediction(data);
  }
}

Repare que o tipo do parâmetro é PredictionRepository — a interface, não uma implementação. A classe declara "eu preciso de algo com este formato" e aceita qualquer coisa que se encaixe: o mock, o SQLite, um fake de teste. Quando o use case precisa de três dependências, como SettlePendingPredictions, o construtor simplesmente lista as três.

2. implements transforma o contrato em erro de compilação

Escrever class SQLiteMatchRepository implements MatchRepository não é decoração: o TypeScript passa a exigir que todos os métodos do contrato existam, com os tipos exatos. Esquecer um método ou trocar o retorno de Promise<Match | null> para Promise<Match> quebra o build antes de o app rodar.

É isso que torna a substituição de implementações segura. Sem essa checagem, "trocar o mock pelo Firestore" seria um ato de fé — com ela, o compilador garante que a peça nova encaixa no mesmo buraco.

3. Forma previsível: uma classe, um execute()

São 28 use cases no projeto e todos têm exatamente a mesma silhueta: construtor com dependências, um único método público execute(). Você sabe como o arquivo é antes de abri-lo, e sabe onde procurar a regra de negócio de qualquer funcionalidade.

Essa uniformidade tem um retorno prático: com todos os use cases tendo a mesma forma, eles viram peças intercambiáveis. É o que permite a factory makeSettlePendingPredictions compor makeAddUserCoins().execute(...) como recompensa, sem que o domínio de apostas saiba absolutamente nada sobre álbum.

Convenção do projeto ≠ lei da arquitetura

"Cada classe tem um método só" não é regra de Clean Architecture — é convenção deste projeto. O que a arquitetura pede vem do princípio da responsabilidade única (SRP): uma razão para mudar, não um método. São coisas diferentes: uma classe pode ter cinco métodos e uma só razão para mudar, ou um método e três razões.

Um método, várias regras — e por que isso está certo

A confusão mais comum aqui é achar que um método significa uma regra. Não significa. A convenção fala do método público, ou seja, da porta de entrada — não do tamanho do que existe lá dentro.

Um use case corresponde a uma intenção do usuário: "comprar um pacote". Essa única intenção envolve várias regras, e elas pertencem juntas justamente porque servem à mesma intenção:

domain/usecases/BuyStickerPack.ts um execute(), cinco regras
async execute(userId, albumId, cost) {
  const coins = await repo.getUserCoins(userId);
  if (coins < cost) throw new Error('Saldo insuficiente');  // regra 1

  const drawn = drawStickersWithRepetition(pool, PACK_SIZE, ...); // regra 2
  const drawnIds = [...new Set(drawn.map((s) => s.id))];         // regra 3

  await repo.commitStickerPurchase({
    newBalance: coins - cost,                                // regra 4
    progress: computeCollectionProgress(...),                // regra 5
    ...
  });
}

O limite não é a quantidade de regras — é se elas mudam pelo mesmo motivo. Se BuyStickerPack também atualizasse o ranking e disparasse uma notificação, aí sim seria cheiro: são intenções diferentes, que mudam por razões diferentes, e mereceriam use cases separados.

A válvula de escape

Repare no código acima: o execute() tem 23 linhas, mas o cálculo pesado não está nele. drawStickersWithRepetition e computeCollectionProgress são funções puras em domain/constants/, chamadas de lá. Um método público, várias peças testáveis separadamente. É assim que um use case cresce sem inchar — e é o primeiro lugar para onde olhar quando um execute() começa a ficar longo demais para caber na tela.

4. Testar fica trivial — e sem mock de módulo

Talvez o ganho mais concreto no dia a dia. Como a dependência entra pelo construtor, o teste só precisa passar um objeto falso. Não existe jest.mock() interceptando imports, não existe banco de dados subindo, não existe React envolvido:

domain/usecases/CreatePrediction.test.ts
const predictionRepository = {
  createPrediction: jest.fn(async () => expected),
} as unknown as PredictionRepository;

const sut = new CreatePrediction(predictionRepository);   // injeta o falso
const result = await sut.execute(predictionData);

Esse teste roda em milissegundos e vale para qualquer implementação futura do repositório. (sut = "system under test", o objeto que está sendo testado — convenção comum na suíte do projeto.)

Quantos testes uma regra pede?

Consequência direta da seção anterior, e uma pergunta que costuma aparecer: se BuyStickerPack tem 5 regras, por que o arquivo de teste dele tem 9 testes? Porque testes não contam regras — contam caminhos distintos.

Regra prática

Toda regra que envolve uma comparação (<, <=, >) pede pelo menos dois testes — um de cada lado da fronteira. Foi exatamente o if (coins < cost) que gerou os dois primeiros da tabela: se alguém trocar por <=, só o teste do "saldo exatamente igual" quebra. Um teste só nunca pegaria isso.

Onde o projeto deliberadamente NÃO usa classes

Clean Architecture não exige classes — dava para escrever os use cases como funções que recebem o repositório por parâmetro, e o resultado seria arquitetonicamente idêntico. O que a arquitetura exige é a injeção de dependência e o contrato. A classe é a forma que este projeto escolheu para expressar isso de maneira consistente e legível; a regra de ouro continua sendo a direção dos imports, não a palavra class.

05 — Organização

Como isso vira pastas de verdade

O código é dividido por feature (funcionalidade) — album, apostas, times, grupos, auth — e cada feature repete internamente as mesmas 4 camadas. Isso deixa fácil achar qualquer coisa: se você quer entender apostas, tudo sobre apostas mora dentro de uma única pasta.

estrutura simplificada
src/features/apostas/
  domain/
    entities/        Match, Prediction — os "tipos" de dado
    usecases/        GetUpcomingMatches, CreatePrediction...
  infra/
    repositories/    implementações concretas (mock ou Firestore)
  main/
    factories/       makeCreatePrediction, makeGetUpcomingMatches...
  presentation/
    hooks/           useCreatePrediction, useUpcomingMatches...
    components/      ContainerAposta, BotaoHistorico...

Fora das features, existe src/shared/ para tudo que é reaproveitado por vários lugares — tema visual, o usuário logado, componentes genéricos como a barra de navegação.

06 — Navegação

Rotas com Expo Router

O Expo Router usa roteamento baseado em arquivos: o nome e o local do arquivo dentro da pasta app/ definem automaticamente qual é a URL/rota daquela tela — não existe um arquivo central listando "rota X vai para componente Y", como em React puro.

  • app/(tabs)/times.tsx → vira a aba "Times" na barra inferior.
  • app/mercado/[albumId].tsx → rota dinâmica; o [albumId] vira um parâmetro que a tela recebe (qual álbum abrir).
  • app/apostas.tsx → configurado no layout raiz para abrir como um modal (uma tela que sobe por cima da atual).
Convenção do projeto

Os arquivos dentro de app/ são só "casquinhas" (shells) que importam a tela de verdade de dentro da feature (ex: TimesScreen em src/features/times/presentation/screens/). Nenhuma lógica de negócio fica dentro da pasta app/.

07 — Na prática

Fluxo ponta a ponta: abrir um pacote de figurinhas

Para amarrar tudo, veja o caminho completo de uma ação real do usuário — do toque na tela até o banco de dados na nuvem e de volta:

  1. 1 Presentation Usuário toca em "Abrir Pacote"

    O componente da tela chama uma função exposta pelo hook useBuyStickerPack.

  2. 2 Presentation O hook assume o estado de "carregando"

    Ele marca loading: true e, por baixo dos panos, pede o use case pronto à Main.

  3. 3 Main A factory monta a peça

    makeBuyStickerPack() cria o use case já injetado com o repositório singleton do Firestore.

  4. 4 Domain O use case roda a regra de negócio

    BuyStickerPack.execute() confere o saldo, sorteia PACK_SIZE figurinhas e recalcula o progresso — tudo em memória. Ele não sabe se os dados vêm da nuvem ou de um mock: só conversa com a interface AlbumRepository.

  5. 5 Infra O Firestore é consultado e atualizado

    FirestoreAlbumRepository.commitStickerPurchase() recebe o resultado já decidido — saldo novo, ids e progresso — e grava tudo numa única escrita no documento do usuário (mais detalhes na seção 08). Ele não decide nada.

  6. 6 Presentation O resultado sobe de volta e a tela reage

    O hook recebe as figurinhas sorteadas, atualiza o estado, e dispara a animação de abertura do pacote (efeito "gacha" feito com react-native-reanimated).

Repare que cada seta do diagrama da seção 02 aparece aqui como um passo concreto — essa é a utilidade real da arquitetura: qualquer pessoa consegue prever por onde o código passa antes mesmo de abrir o arquivo.

08 — Persistência

Banco de dados não-relacional (Firestore)

Um banco relacional (SQL, como PostgreSQL ou SQLite) guarda dados em tabelas com colunas fixas e obrigatórias — todo registro de uma tabela tem exatamente o mesmo formato. Um banco não-relacional (NoSQL) como o Firestore guarda dados em documentos: blocos de informação parecidos com um objeto JSON, agrupados em coleções, sem exigir que todo documento tenha os mesmos campos.

SQL — tabela
idcoinsprogress
user_120012.5
user_23408.0
Firestore — documento
users/
user_1 {
coins: 200,
stickerIds: ["s12", "s47"],
progress: 12.5
}

No Popular da Copa, cada usuário é um documento dentro da coleção users, identificado pelo próprio id do usuário. Os campos desse documento (moedas, figurinhas possuídas, progresso do álbum) ficam soltos ali dentro — sem precisar de uma tabela separada para cada tipo de dado.

Como o código conversa com o Firestore

Três operações do SDK do Firebase aparecem bastante no repositório e valem a pena entender:

  • increment(n) — soma n a um campo numérico direto no servidor, evitando o problema de "ler o valor antigo, somar e escrever" com informação desatualizada.
  • arrayUnion(...ids) — adiciona itens a uma lista dentro do documento sem duplicar os que já existem.
  • serverTimestamp() — grava a hora oficial do servidor do Firebase, em vez de confiar no relógio do celular do usuário (importante para o cálculo do cooldown de 24h da recompensa diária).

Um detalhe curioso da implementação

O projeto teve um bug de configuração real: o banco no Google Cloud estava nomeado literalmente default em vez do padrão (default) com parênteses, e isso fazia o SDK devolver "banco não encontrado". A correção foi passar o nome do banco explicitamente ao inicializar o Firestore — um bom lembrete de que erros de infraestrutura às vezes não têm nada a ver com a lógica do código.

09 — Critério de decisão

Regra de ouro: o que vai onde

O projeto usa dois tipos de armazenamento por um motivo de performance e custo: bancos na nuvem cobram (e demoram um pouco) por cada leitura e escrita, então só o que realmente muda ou é pessoal do usuário vai para lá. Tudo o que é fixo fica salvo localmente no próprio app.

Tipo de dadoOnde ficaExemplos no projeto
Estático — igual para todo mundo, não muda durante o uso do app SQLite local Lista de seleções/países, regras fixas do jogo, estrutura dos pacotes de figurinha
Mutável ou pessoal — pertence a um usuário específico, muda com frequência Firestore (nuvem) Saldo de moedas, figurinhas possuídas, progresso do álbum, histórico de palpites, dados da conta

Vale notar que, hoje, os dados "estáticos" de figurinhas e álbuns (seção 9.5 da documentação técnica) ainda vivem em arquivos de seed (dados fixos de exemplo) dentro do próprio Infra — o SQLite local para esse propósito é um passo planejado, não implementado por completo ainda.

10 — Padrões

Decisões técnicas que vale a pena entender

Sem Redux/Zustand Estado local em cada hook já resolve; o usuário logado global usa só Context API (um jeito nativo do React de compartilhar dado sem precisar passar por props em cada componente).
Singleton de repositório Cada feature mantém uma única instância do repositório (singleton = "só existe um"), assim o estado não se perde ao navegar entre telas.
Um execute() por use case Todo use case segue a mesma "forma": uma classe, um método público execute(). Fica previsível, fácil de testar e de compor. Atenção: um método não quer dizer uma regra — dentro dele podem morar várias, desde que sirvam à mesma intenção do usuário (ver seção 04).
Datas como texto (ISO) Datas circulam como string no formato ISO (ex: "2026-07-27T10:00:00Z") em vez de objeto Date, evitando bugs de serialização ao transformar em JSON. Só vira Date de fato na tela, na hora de formatar.
Ionicons, nunca emoji Todo ícone da interface usa a biblioteca @expo/vector-icons (Ionicons) em vez de caracteres de emoji cru — garante aparência consistente entre Android e iOS.
11 — Referência rápida

Glossário

Composition Root
O único ponto do programa onde as peças concretas (banco de dados, etc.) são montadas e entregues prontas para o resto do código usar. Aqui é a camada Main.
Repository Pattern
Um "contrato" (interface) que descreve as operações de dados disponíveis (buscar, salvar...), sem dizer de onde os dados vêm de fato.
Injeção de dependência
Em vez de uma classe criar suas próprias dependências, elas chegam prontas "de fora" (por parâmetro do construtor, por exemplo) — facilita trocar uma peça por outra.
Inversão de dependência
Quando a camada de fora se submete ao contrato definido pela camada de dentro. Aqui: o Domain declara a interface e a Infra a implementa — por isso a Infra importa o Domain, e nunca o contrário.
Interface (contrato)
Descrição de quais métodos algo precisa ter, sem dizer como eles funcionam. Some na compilação: existe só para o TypeScript checar que a peça encaixa.
sut
System under test — nome dado nos testes ao objeto que está sendo testado, para distingui-lo dos dublês (mocks/fakes) ao redor.
Hook (React)
Uma função especial que guarda estado e lógica reutilizável dentro de componentes React — aqui, cada tela usa hooks próprios para buscar e guardar seus dados.
Singleton
Padrão de projeto em que só existe uma única instância de algo durante a vida do programa.
NoSQL / documento
Banco de dados que guarda informação em blocos flexíveis (documentos), em vez de tabelas com colunas fixas.
Coleção (Firestore)
Um agrupamento de documentos do mesmo tipo — equivalente, de forma solta, a uma "tabela" no mundo SQL.
Seed
Dado fixo de exemplo, escrito à mão no código, usado para popular o app durante o desenvolvimento (times, figurinhas, partidas).
Roteamento baseado em arquivo
Técnica do Expo Router em que a estrutura de pastas/arquivos define automaticamente as rotas do app.
Debounce
Técnica para "esperar o usuário parar de digitar" antes de disparar uma ação (usado na busca de times, com 500ms de espera).
