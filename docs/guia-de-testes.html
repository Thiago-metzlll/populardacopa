00 — Fundamento

O que é um teste unitário

Um teste unitário é um pedaço de código que executa uma única "unidade" do sistema (uma função, uma classe, um hook, um componente) de forma isolada, e verifica automaticamente se o resultado é o esperado. "Isolada" é a palavra-chave: se o teste precisa de internet, de um celular ou de um banco de dados de verdade para passar, ele não é mais unitário — vira teste de integração, que é mais lento e falha por motivos que não têm nada a ver com o código.

A ferramenta usada aqui é o Jest, que executa os testes em Node.js — ou seja, no computador, sem emulador e sem celular. Isso é o que permite rodar as 535 verificações em cerca de 25 segundos.

A anatomia de um teste

Todo arquivo de teste usa três funções globais do Jest, e segue o padrão AAA (Arrange, Act, Assert — prepare, execute, verifique):

src/features/album/domain/constants/rewards.test.tsexemplo real
describe('computeDailyClaimStatus', () => {   // agrupa testes relacionados
  it('bloqueia antes do fim do cooldown', () => {  // um caso de teste

    // ARRANGE — monta a situação
    const now = new Date('2026-07-28T12:00:00.000Z');
    const lastClaimedAt = new Date('2026-07-28T00:00:00.000Z').toISOString();

    // ACT — executa a unidade sob teste
    const status = computeDailyClaimStatus(lastClaimedAt, DAILY_REWARD_COOLDOWN_MS, now);

    // ASSERT — afirma o que deveria ter acontecido
    expect(status.available).toBe(false);
    expect(status.nextAvailableAt).toBe('2026-07-29T00:00:00.000Z');
  });
});

Repare que now é passado por parâmetro, em vez de a função chamar new Date() internamente. Esse detalhe é o que torna o teste possível: uma função que lê o relógio do sistema sozinha daria um resultado diferente a cada execução. Voltaremos a isso na seção 07.

Conceito fundamental

Mock (ou dublê) é uma peça falsa que ocupa o lugar de uma dependência real durante o teste. Em vez de conversar com o Firestore de verdade, o teste entrega ao código um objeto que finge ser o Firestore, devolve respostas combinadas na hora, e ainda registra tudo o que foi chamado — o que permite afirmar depois: "o código gravou exatamente estes dados".

Uma nota de nomenclatura que aparece em todo o projeto: a variável chamada sut significa System Under Test — o objeto que está sendo testado naquele arquivo, para distingui-lo dos mocks ao redor.

01 — Arquitetura de dados

Grafo de fluxo de informações

Antes de falar do que os testes fazem, é preciso enxergar por onde a informação anda. O app tem três destinos de dados diferentes, escolhidos por um critério simples (a "regra de ouro" da documentação técnica): dado estático e igual para todos mora no SQLite local (dentro do aparelho, sem internet, sem custo); dado pessoal e mutável mora no Firestore (nuvem); e identidade (quem é o usuário logado) é responsabilidade da API de autenticação do Firebase.

02 — O princípio central

A fronteira do mock: onde o teste corta

Toda a estratégia de testes deste projeto cabe em uma frase: o teste substitui o vizinho mais próximo, nunca a fonte inteira. Em cada camada, o dublê é colocado exatamente um passo adiante do que está sendo testado — nem mais perto (o que testaria só o mock), nem mais longe (o que exigiria banco de verdade).

Ao testar…o que é substituídocomo
Use case O repositório inteiro Objeto literal com jest.fn() por método, injetado no construtor — repositórios são interfaces TypeScript, então não há classe a instanciar
Repositório SQLite Só o acesso ao driver: getSQLiteDb() jest.mock('.../sqlite/database') devolvendo um fake com getFirstAsync/getAllAsync. O SQL de verdade continua sendo verificado — como string, na asserção
Repositório Firestore Os módulos firebase/firestore e firebaseConfig Sem o segundo, o simples import dispara a validação de variáveis de ambiente e tenta inicializar o Firebase de verdade
Hook A factory do use case (makeX) e o UserContext jest.mock no módulo da factory, devolvendo { execute }. O hook nunca sabe que o repositório existe
Componente Ícones, SVGs e o que o Jest não sabe transformar Infra reutilizável em test/ (seção 10)
Por que isso funciona tão bem aqui

É um efeito direto da Clean Architecture. Como o Domain só conhece interfaces de repositório, e a Presentation só conhece factories, cada camada já tem um ponto de corte natural desenhado na arquitetura. Testar ficou barato porque o código já era desacoplado — não o contrário.

03 — Infraestrutura

Como o Jest foi configurado

Testar React Native fora do celular exige um preset — um pacote de configuração pronta que ensina o Jest a entender JSX, TypeScript e os módulos nativos do Expo. Aqui é o jest-expo.

jest.config.jsraiz do projeto
module.exports = {
  preset: 'jest-expo',                              // entende Expo + RN + TS
  setupFilesAfterEnv: ['<rootDir>/test/setup.tsx'], // mocks globais
  moduleNameMapper: {
    '\\.svg$': '<rootDir>/test/svgMock.tsx',          // SVG → View falsa
    '^@/assets/(.*)$': '<rootDir>/assets/$1',        // espelha o tsconfig
    '^@/(.*)$': '<rootDir>/src/$1',
  },
  collectCoverageFrom: [
    'src/**/*.{ts,tsx}',
    '!src/**/presentation/screens/**',             // telas ficam de fora
    '!src/declarations.d.ts',
  ],
};
  • moduleNameMapper — redireciona um import para outro arquivo. Serve para dois propósitos aqui: replicar os atalhos de caminho do tsconfig.json (@/algo) e trocar arquivos que o Jest não consegue processar (todo .svg vira um mock).
  • setupFilesAfterEnv — código que roda antes de cada suíte, usado para os mocks globais (ícones).
  • collectCoverageFrom — define o que entra no cálculo de cobertura. As *Screen.tsx são excluídas de propósito: são só composição de hooks e componentes já testados individualmente.

Convenção de arquivos

O teste mora ao lado do arquivo testado: rewards.ts → rewards.test.ts. Sem pasta __tests__ separada, sem configuração extra (o testMatch padrão do Jest já reconhece o sufixo). A vantagem prática: abrir o código e ver imediatamente se ele é testado.

A exceção é a pasta test/ na raiz, fora de src/, que guarda infraestrutura compartilhada — fixtures.ts, styleHelpers.ts, svgMock.tsx, setup.tsx.

04 — Estratégia

Quanto testar de cada camada

Nem toda camada merece o mesmo esforço. O critério usado foi densidade de lógica por unidade de atrito: onde há regra de negócio de verdade e nenhum mock difícil, cobertura total; onde há muito mock e pouca lógica, cobertura seletiva.

Domain

Funções puras e use cases. Zero mock de módulo nativo, toda a regra do jogo. Cobertura completa de casos.

prioridade máxima

Infra

Repositórios: mapeamento linha→entidade, montagem de query, guardas de erro. Mocka-se o driver, não o repositório.

alta

Hooks

Estados loading/error/data, tradução de erro, efeitos e limpeza. Cobertura completa das 5 features.

alta

Componentes

Só o que ramifica: estilo condicional por raridade/estado, formatação, interação. Nada de snapshot.

seletiva — 13 componentes

Fora do escopo

*Screen.tsx (composição do que já é testado), animações puras (AnimacaoAbrirPacote, ChargeGlow, Particle) e as factories make*.ts.

decisão consciente

O padrão que definiu a estratégia

Ao mapear os use cases existentes, uma constatação mudou o plano: a maioria é delegação pura de uma linha ao repositório.

src/features/album/domain/usecases/AddUserCoins.ts
export class AddUserCoins {
  constructor(private readonly albumRepository: AlbumRepository) {}

  async execute(userId: string, amount: number) {
    return this.albumRepository.addUserCoins(userId, amount); // e só
  }
}

Não há o que quebrar aqui. Então esses casos recebem um teste de contrato curto — "chama o método certo, com os argumentos certos, e devolve o resultado sem transformar" — que funciona como rede de segurança se a lógica crescer depois. A lógica de negócio real estava concentrada em poucos arquivos, e é lá que a cobertura é exaustiva.

Quando a delegação é sintoma, não escolha

Cuidado com uma leitura fácil demais: um use case de uma linha pode significar que a operação não tem regra — ou que a regra dele foi parar na camada errada. Foi o caso de BuyStickerPack e BuyIndividualSticker: eram uma linha cada porque conferir saldo, sortear e recalcular progresso estava tudo dentro do FirestoreAlbumRepository. Hoje as regras voltaram para os use cases e o repositório só persiste. O sinal de alerta é o nome: um use case que leva o nome de uma operação e não contém nenhuma decisão dela merece uma olhada na Infra.

05 — Leitura crítica

Cobertura de 100% não é qualidade de 100%

A seção anterior explicou por que os use cases delegantes recebem só um teste de contrato. Esta seção mostra o resultado disso em números — e por que esses números enganam se lidos sem contexto. É a leitura mais importante do guia inteiro.

Rodando a cobertura restrita aos 28 use cases do projeto:

14% dos use cases concentram 52% dos testes. Os quatro são BuyStickerPack (9 testes), BuyIndividualSticker (8), SettlePendingPredictions (7 — único com for, if aninhado e três dependências injetadas) e GetUserProfile (4). Os outros 24 são uma linha cada.

Os dois primeiros entraram nessa lista depois: até pouco tempo eram delegação pura de uma linha, com um teste de contrato cada. Não porque a funcionalidade mudou, mas porque as regras de compra — recusar por saldo insuficiente, sortear PACK_SIZE figurinhas, recalcular progresso — foram trazidas do repositório de volta para o use case, que é onde regra de aplicação pertence. O ganho de teste foi imediato: com random e o relógio injetáveis no construtor, a compra virou determinística e passou a ser testável sem Firestore nenhum.

O que a métrica realmente mede

Cobertura responde a uma pergunta só: esta linha foi executada durante os testes? Ela não sabe se você verificou alguma coisa depois de executá-la. Um teste sem nenhum expect deixa a linha 100% coberta e não detecta defeito nenhum.

No caso dos 24 delegantes, cobrir 100% de AddUserCoins.execute() significa chamar uma linha uma vez. O teste não valida regra de negócio, porque não existe regra ali — ela mora no repositório, e é coberta pelos testes de FirestoreAlbumRepository (17 testes), SQLiteTeamRepository (14) e das funções puras em domain/constants/. O valor desses 24 é outro, e é real: contrato e regressão.

Um teste de contrato......pega...não pega
Alguém trocar o método chamado sim —
Inverter a ordem dos argumentos sim —
Passar a transformar o retorno sem querer sim —
O SELECT do repositório estar errado — não — é o teste de Infra
O cálculo de cooldown estar errado — não — é o teste de constants

Um caso concreto: o número que os 100% escondiam

Antes desta revisão a cobertura dos use cases estava em 100% de statements, linhas e funções — mas 95,83% de branches. Um único ramo descoberto, em SettlePendingPredictions:

domain/usecases/SettlePendingPredictions.ts linha 45
if (won) {
  if (prediction.reward.type === 'coins' && prediction.reward.coinAmount) {
    await this.rewardGranter.grantCoins(userId, prediction.reward.coinAmount);
  } else if (prediction.reward.type === 'sticker' && prediction.reward.stickerIds) {
    await this.rewardGranter.grantStickers(userId, prediction.reward.stickerIds);
  }
  // ← e se nenhum dos dois casar? o palpite é liquidado, a recompensa evapora
}

Um palpite vencedor com type: 'sticker' mas sem stickerIds — ou type: 'coins' sem coinAmount — cai fora dos dois ramos: o status vira 'won', o usuário vê que acertou, e não recebe nada. Nenhuma exceção, nenhum log. Não é hipótese: um seed malformado ou um campo opcional esquecido produz exatamente isso.

As três métricas em 100% não apontavam para lá. Só o branch coverage apontava — e por isso é a métrica que vale acompanhar. Foi acrescentado o teste 'marca como vencedora mas não concede nada quando a recompensa está malformada', que documenta o comportamento atual e fecha o ramo. Hoje a cobertura dos use cases está em 100% nas quatro métricas.

Como ler cobertura sem se enganar

Cobertura alta não prova que o código está certo — prova que o código foi executado. Ela serve bem como detector de ausência ("isto aqui ninguém testou") e mal como certificado de presença ("isto aqui está testado"). Quando as quatro métricas divergem, a menor delas costuma ser a que está dizendo a verdade.

06 — Mapa

Onde cada arquivo de teste mora

O projeto não tem pasta __tests__ nem diretório tests/ espelhando a árvore do código. A convenção é co-locação: o teste fica no mesmo diretório do arquivo que testa, com o sufixo .test.ts (ou .test.tsx quando renderiza componente). CreatePrediction.ts e CreatePrediction.test.ts são vizinhos.

A vantagem é direta: ao abrir qualquer pasta você vê imediatamente o que tem e o que não tem teste, sem navegar em paralelo por duas árvores. A única exceção é test/ na raiz, que guarda a infraestrutura compartilhada da suíte (setup, mocks globais, fixtures) — não testa nada por si só.

07 — Camada Domain

Testando regra de negócio pura

Esta é a camada mais fácil e mais valiosa de testar: sem React, sem banco, sem rede. Uma função entra com valores, sai com valores.

Injeção de determinismo: o truque central

Determinismo significa: mesma entrada, mesma saída, sempre. Duas coisas quebram isso — o relógio (new Date()) e o acaso (Math.random()). A solução adotada em todo o projeto é a mesma: transformar essas fontes em parâmetros com valor padrão. O app em produção não passa nada e usa o padrão; o teste passa um valor fixo e controla o resultado.

o padrão, em duas assinaturas reais
// relógio injetável
export function computeDailyClaimStatus(
  lastClaimedAt: string | null,
  cooldownMs: number,
  now: Date = new Date(),          // ← padrão em produção, fixo no teste
) { /* ... */ }

// acaso injetável
export function generatePlayerStats(
  position: string,
  random: () => number = Math.random,  // ← idem
) { /* ... */ }

Com isso, um teste pode afirmar coisas impossíveis de outra forma: "defensor só marca gol quando o sorteio passa de 0.8" vira uma asserção exata, não uma estatística.

A refatoração que os testes provocaram

Ao tentar testar o FirestoreAlbumRepository, ficou claro que ele misturava regra de negócio (sorteio de figurinhas, cálculo de progresso) com chamadas ao Firestore no mesmo método — intestável sem mockar Math.random no meio de uma cadeia de getDoc/updateDoc. O mesmo defeito apareceu em outros repositórios. A resposta foi extrair essas regras para funções puras em domain/constants/:

Lição de projeto

Foi uma refatoração pura: nenhum comportamento observável do app mudou, os repositórios apenas passaram a chamar as funções extraídas. Vale como o argumento mais concreto a favor de testar — a dificuldade de escrever o teste apontou um problema de design que já existia no código de produção.

Teste de contrato, na prática

padrão dos use cases delegantes
const albumRepository = { buyStickerPack: jest.fn() } as unknown as AlbumRepository;

it('delega a compra para o repositório com os argumentos recebidos', async () => {
  const sut = new BuyStickerPack(albumRepository);

  await sut.execute('u1', 'a1', 100);

  expect(albumRepository.buyStickerPack).toHaveBeenCalledWith('u1', 'a1', 100);
});

Como os repositórios são interfaces TypeScript (não classes), o mock é só um objeto literal com jest.fn() nos métodos usados — nenhuma biblioteca de mocking extra é necessária.

08 — Camada Infra

Testando repositórios sem banco de dados

Aqui o teste chega na fronteira vermelha do grafo. Não existe SQLite nem Firestore rodando em Node — e nem se quer que exista. A regra: mockar o ponto de acesso ao driver, não o repositório inteiro. Mockar o repositório inteiro não testaria nada; mockar só o driver deixa intactos o SQL, o mapeamento e as guardas de erro — que é exatamente o que essa camada faz de errado quando erra.

SQLiteAlbumCatalogRepository.test.tsestrutura completa
// 1. o mock vem ANTES dos imports — ver a pegadinha do hoisting na seção 11
jest.mock('../../../../shared/infra/sqlite/database', () => ({
  getSQLiteDb: jest.fn(),
}));

import { getSQLiteDb } from '../../../../shared/infra/sqlite/database';
import { SQLiteAlbumCatalogRepository } from './SQLiteAlbumCatalogRepository';

// 2. o "banco" falso: só os dois métodos que o repositório usa
const mockDb = { getFirstAsync: jest.fn(), getAllAsync: jest.fn() };

beforeEach(() => {
  jest.clearAllMocks();                       // isola cada teste do anterior
  (getSQLiteDb as jest.Mock).mockResolvedValue(mockDb);
});

it('mapeia a linha do banco para a entidade Album', async () => {
  // 3. a "linha" que o banco devolveria — snake_case, como no schema
  mockDb.getFirstAsync.mockResolvedValue({
    id: 'a1', name: 'Copa 2026', total_stickers: 500, price: 10,
  });

  const album = await sut.getAlbumById('a1');

  // 4. duas asserções: a query certa E a entidade certa (camelCase, tipada)
  expect(mockDb.getFirstAsync).toHaveBeenCalledWith(
    'SELECT * FROM albums WHERE id = ?;', ['a1'],
  );
  expect(album).toEqual({
    id: 'a1', name: 'Copa 2026', totalStickers: 500, ownedStickersCount: 0, price: 10,
  });
});

O que esse tipo de teste realmente pega

  • Tradução de nomes — o schema SQL usa total_stickers, o domínio usa totalStickers. Um erro de digitação aqui só apareceria na tela, em runtime.
  • Guardas de erro — getAlbumById deve lançar Album not found: x quando a linha não existe, em vez de devolver undefined silenciosamente.
  • Montagem dinâmica de query — getStickersByIds monta os ? do IN (?, ?, ?) conforme a quantidade de ids, e faz early return sem tocar no banco quando a lista está vazia.
  • Conversões — null do banco vira undefined no domínio; a coluna de raridade recebe cast para o tipo literal.
  • Regras condicionais — em SQLiteMatchRepository, odds só aparecem em partida scheduled, placar só em finished.
  • N+1 queries — getAllGroups faz uma consulta por grupo para a classificação; o teste encadeia mockResolvedValueOnce para simular cada chamada em sequência.
  • Erro engolido — getFavoriteTeams tem um try/catch que devolve [] se o Firestore falhar, em vez de propagar; o teste documenta isso explicitamente.

Os dois casos mais difíceis

FirebaseAuthRepository exigiu três mocks: firebase/auth, firebase/firestore e o módulo firebaseConfig. O terceiro é o não-óbvio — sem ele, o simples import executa a validação de variáveis de ambiente do arquivo e lança erro antes de o primeiro teste rodar.

FirestoreAlbumRepository é o mais complexo da suíte por dois motivos. Primeiro, ele depende de uma classe concreta (SQLiteAlbumCatalogRepository), não de uma interface — o mock precisa de as unknown as jest.Mocked<...> para contornar os campos private da classe real, que quebrariam a checagem estrutural do TypeScript. Segundo, como o mock do Firestore não simula estado real, não adianta gravar e reler: os testes verificam a chamada a updateDoc — o que foi gravado — em vez de uma releitura pós-gravação.

09 — Presentation

Testando hooks

Um hook é uma função React que guarda estado e lógica reutilizável. Neste projeto, cada tela tem hooks próprios que fazem o trabalho de "buscar dados, marcar carregando, tratar erro". Testá-los exige renderizá-los fora de qualquer componente — é o que o renderHook da Testing Library faz.

useLogin.test.tso vocabulário completo
jest.mock('../../main/factories/makeAuth', () => ({ makeSignInWithEmail: jest.fn() }));

const execute = jest.fn();
beforeEach(() => {
  jest.clearAllMocks();
  (makeSignInWithEmail as jest.Mock).mockReturnValue({ execute });
});

it('mantém loading true enquanto a requisição não resolve', async () => {
  // promessa que só resolve quando o teste mandar — congela o "meio do caminho"
  let resolveLogin: (v: unknown) => void = () => {};
  execute.mockReturnValue(new Promise((resolve) => { resolveLogin = resolve; }));

  const { result } = renderHook(() => useLogin());

  act(() => { void result.current.execute('a@a.com', 'senha123'); });

  await waitFor(() => expect(result.current.loading).toBe(true));

  await act(async () => { resolveLogin({ uid: 'u1' }); });

  expect(result.current.loading).toBe(false);
});
  • renderHook — monta um componente invisível só para hospedar o hook; result.current é sempre o retorno mais recente.
  • act — envolve qualquer coisa que cause atualização de estado, garantindo que o React processe o re-render antes da asserção. Sem isso, o teste lê um estado velho e o Jest imprime um aviso.
  • waitFor — repete a asserção até ela passar (ou estourar o tempo). É o que permite testar estados assíncronos sem sleep.
  • Promessa controlada manualmente — a técnica acima é a única forma de observar o estado intermediário (loading: true), que normalmente dura microssegundos.

Testando componentes visuais

É a camada de maior atrito: o Jest não sabe lidar com SVG, fontes de ícone, gradientes nem animações nativas. Três peças reutilizáveis em test/ resolveram isso de uma vez para todos os testes.

ArquivoProblema que resolve
test/svgMock.tsx O react-native-svg-transformer não roda sob Jest, então todo import Flag from '...svg' quebraria. Mapeado via moduleNameMapper, cada SVG vira <View testID="svg-flag" />
test/setup.tsx O @expo/vector-icons carrega a fonte de forma assíncrona e chama setState fora de act(), poluindo a saída de todo teste com avisos. O mock troca o ícone por <Text testID="icon-{name}"> — o que, de quebra, permite asserir qual ícone cada estado renderiza
test/styleHelpers.ts flattenStyle, collectStyles, hasStyle, collectProps: percorrem a árvore renderizada para verificar estilo condicional sem espalhar testID de teste pelo código de produção
test/fixtures.ts makeUser, makeSticker, makeTeam, makePlayer, makeMatch: entidades completas com overrides parciais, para o teste declarar só o campo que importa naquele caso

Testar ramificação, não aparência

Nenhum teste aqui usa snapshot (foto da saída renderizada). Snapshots quebram a cada ajuste de layout e não afirmam nada sobre comportamento. O foco é no que ramifica: uma prop diferente deve produzir um resultado visual diferente.

CardFigurinha/index.test.tsxuma tabela, três casos
it.each([
  ['comum',    ['#3A3A40', '#24242B'], '#555',    '○'],
  ['rara',     ['#1a1a4e', '#24242B'], '#4488FF', '●'],
  ['lendaria', ['#3d2000', '#24242B'], '#FFD700', '★'],

  render(<CardFigurinha sticker={makeSticker({ rarity })} />);

  expect(gradientProps().colors).toEqual(colors);
  expect(flattenStyle(gradientProps().style).borderColor).toBe(border);
  expect(screen.getByText(symbol)).toBeTruthy();

it.each gera um teste por linha da tabela — três casos com uma implementação só, e a falha aponta exatamente qual raridade quebrou. Outros focos cobertos: MolduraIndividualPais (mapeamento ISO-3 → ISO-2 das 48 seleções, sub-regiões como sco → gb-sct, SVG local vs. fallback remoto) e os cards de recompensa, que usam fake timers — um relógio falso do Jest — para adiantar o contador regressivo sem esperar de verdade.

11 — Aprendizados

Pegadinhas reais encontradas

Esta seção é a mais útil para estudar: são erros que só aparecem escrevendo testes de verdade, e cada um deles custou tempo neste projeto.

1. jest.mock sobe para o topo do arquivo

O Jest move (hoisting) todas as chamadas de jest.mock para antes dos import, mesmo que você as escreva depois. Isso é necessário — o mock precisa existir antes de o módulo ser carregado —, mas gera uma armadilha: a função de fábrica do mock não pode referenciar variáveis declaradas fora dela, porque elas ainda não existem no momento em que roda.

a armadilha e a saída
// ✗ ReferenceError: Cannot access 'React' before initialization
import React from 'react';
jest.mock('@expo/vector-icons', () => ({ Ionicons: () => React.createElement(...) }));

// ✓ require() dentro da fábrica, resolvido só na hora da chamada
jest.mock('@expo/vector-icons', () => {
  const React = require('react');
  const { Text } = require('react-native');
  return { Ionicons: ({ name, ...props }) =>
    React.createElement(Text, { testID: `icon-${name}`, ...props }, name) };
});

2. npm test não verifica tipos

Descoberta desconfortável: describe, it, expect e jest estavam com erro de tipo em todo arquivo de teste desde o primeiro dia — e ninguém percebeu, porque o Jest compila com Babel, que apaga os tipos sem checá-los. Só rodar tsc --noEmit revelou. Duas causas:

  1. Faltava "types": ["jest"] no tsconfig.json — sem isso o TypeScript não carrega o @types/jest, mesmo instalado.
  2. @types/jest declara jest como namespace de tipos (jest.Mock), não como valor — daí o erro "Cannot use namespace as a value" em jest.fn(). Resolvido instalando @jest/globals e mesclando o tipo no escopo global via src/declarations.d.ts.
Consequência prática

Testes passando não são prova de código correto do ponto de vista de tipos. Por isso o projeto ganhou um script dedicado npm run typecheck, que roda separado de npm test — os dois precisam estar limpos.

3. O teste documenta o comportamento real, não o esperado

Três casos em que a suíte registra um comportamento que talvez seja um defeito, em vez de fingir que o código faz o "certo":

  • GetUserProfile — o campo stickers retornado não é ordenado; só recentStickers e rareStickers usam a lista ordenada internamente. Um teste ingênuo que assume ordenação falha.
  • CardHistoricoMundial — resultColor testa includes('campeão') antes de includes('vice'), então "Vice-campeão" é pintado de dourado (cor de campeão), não prata. Se a ordem dos if for corrigida, o teste precisa mudar junto — e é justamente esse acoplamento que sinaliza a mudança.
  • useCreatePrediction — o erro que não se limpa, descrito na seção 09.

4. Isolamento entre testes é responsabilidade sua

Mocks guardam histórico de chamadas entre um teste e outro. Sem jest.clearAllMocks() no beforeEach, um toHaveBeenCalledTimes(1) passa sozinho e falha na suíte inteira. O mesmo vale para estado global: os testes de useAbrirPacote chamam pendingPackStore.clear() tanto no beforeEach quanto no afterEach, porque esse store vive fora do React e não é recriado a cada render.

5. Um bug real que os testes fixaram

O hook useAbrirPacote tinha um bug de double-draw: ao reabrir a tela de um pacote já sorteado, ele sorteava figurinhas de novo. A correção foi o pendingPackStore — lê o pacote pendente antes de chamar o sorteio. O teste que verifica isso é a garantia de que a regressão não volta.

Como rodar e o que verificar

terminal

npm run test:watch       # re-roda só o que mudou, enquanto você edita
npm run test:coverage    # relatório de cobertura por camada

npm run typecheck        # tsc --noEmit — precisa estar limpo também
npm run lint             # expo lint

npx jest rewards         # roda só os arquivos cujo caminho casa com "rewards"
npx jest -t "cooldown"     # roda só os it(...) cujo nome contém "cooldown"
Atenção em checkout novo

npm run typecheck depende de .expo/types/router.d.ts, que é gerado pelo Expo Router e está no .gitignore. Num clone limpo, rode npx expo start uma vez antes de confiar no resultado do typecheck — sem isso aparecem erros falsos nas rotas.

Checklist para escrever um teste novo neste projeto

  • O arquivo fica ao lado do original, com sufixo .test.ts / .test.tsx.
  • O nome do it(...) descreve comportamento em português, não implementação: "bloqueia antes do fim do cooldown", não "testa a função X".
  • Identifique a camada e use o ponto de corte dela (tabela da seção 02) — não mocke mais fundo que o necessário.
  • jest.clearAllMocks() no beforeEach, sempre.
  • Se a unidade depende de relógio ou sorteio, injete-os por parâmetro em vez de mockar globais.
  • Reaproveite test/fixtures.ts e declare por override só o campo que o caso exige.
  • Rode npm test e npm run typecheck — um não substitui o outro.
  • Se o comportamento atual parecer errado, escreva o teste do que o código faz e registre a dúvida no teste ou na documentação; não "conserte" de lado.
13 — Referência

Glossário

Jest
Executor de testes que roda em Node.js — encontra os arquivos *.test.ts, executa e reporta o que passou ou falhou.
Suíte
Um arquivo de teste. "61 suítes" = 61 arquivos .test.ts(x) no projeto.
Preset
Pacote de configuração pronta do Jest para um ambiente específico — aqui, jest-expo, que ensina o Jest a entender React Native e Expo.
Mock / dublê
Objeto falso que substitui uma dependência real durante o teste, devolvendo respostas combinadas e registrando as chamadas recebidas.
Fixture
Dado de exemplo pronto para testes (um usuário, uma figurinha), com valores padrão que cada teste sobrescreve parcialmente.
SUT
System Under Test — a unidade que está sendo testada naquele arquivo, por convenção nomeada sut.
AAA
Arrange, Act, Assert — prepare o cenário, execute a ação, verifique o resultado. A estrutura de todo teste.
Determinismo
Mesma entrada, mesma saída, sempre. Quebrado por relógio e sorteio — resolvido injetando os dois por parâmetro.
Hoisting
Movimentação automática de jest.mock para antes dos import, feita pelo Babel. Motivo de erros de "variável não inicializada" dentro de mocks.
Fake timers
Relógio falso do Jest: permite "adiantar" segundos ou horas instantaneamente, para testar contadores e intervalos sem esperar.
act()
Função que garante que o React terminou de processar as atualizações de estado antes da asserção seguinte.
waitFor()
Repete uma asserção até ela passar ou o tempo acabar — usado para estados assíncronos.
Teste de contrato
Verifica apenas que a unidade chama o colaborador certo com os argumentos certos — usado nos use cases de delegação pura.
Cobertura
Percentual de linhas/ramos do código executados pelos testes. Indicador útil, não meta em si: 100% de cobertura sem asserção boa não prova nada.
Snapshot
"Foto" da saída renderizada, comparada a cada execução. Não usado aqui: quebra a cada ajuste visual sem afirmar comportamento.
N+1 query
Padrão em que uma consulta inicial dispara mais uma consulta por resultado — presente em getAllGroups e simulado no teste com mockResolvedValueOnce encadeado.
